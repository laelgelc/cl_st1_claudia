# `describe_music_videos_music.py` — Programme Specification for Development

## 1. High-level Functionality Specification

### Programme Summary

`describe_music_videos_music.py` is a batch-processing programme that generates continuous qualitative descriptions of music video audio files using the Gemini API.

The programme is part of:

```plain text
Corpus Linguistics — Study 1 — Claudia, Phase 1
```

It reads the curated audio index produced by the audio download stage:

```plain text
corpus/01_music_videos_audio/music_videos_audio_index.ndjson
```

Each record in this index represents one eligible music video audio file. The programme must process records where the extracted audio is available, indicated by:

```plain text
download_status = success
```

or:

```plain text
download_status = skipped_existing
```

For each eligible record, the programme uses:

- `corpus_id` to identify the music video;
- `audio_file`, when present and valid, to locate the source WAV file;
- `<input_dir>/<corpus_id>.wav` as a fallback source audio path;
- `corpus_id` again to name description outputs.

The source audio files are expected in:

```plain text
corpus/01_music_videos_audio/audio/
```

Description outputs must be written to:

```plain text
corpus/03_music_videos_music_descriptions/
```

For each successfully described music video, the programme must write:

```plain text
corpus/03_music_videos_music_descriptions/<corpus_id>.txt
corpus/03_music_videos_music_descriptions/<corpus_id>.json
```

The `.txt` file contains a clean plain-text description generated by Gemini intended for corpus analysis and human inspection.

The `.json` file contains detailed generation metadata, including:

- source metadata;
- generated description text;
- model configuration;
- runtime information;
- output paths;
- item status.

The intended analysis engine is:

```plain text
Gemini API
```

The preferred implementation uses the official SDK:

```plain text
google-genai
```

This programme performs **audio description generation only**.

## 2. Key Behaviours

The programme must implement the following behaviours:

- Load the `GEMINI_API_KEY` from a local environment file (e.g., `env/.env`) using `python-dotenv`.
- Read the analysis prompt from a markdown file, defaulting to `music_description_prompts/music_description_prompt_v1.md`.
- Read music video audio metadata from an NDJSON audio index file.
- Process only records where `download_status` indicates usable extracted audio.
- Extract the required field:
  - `corpus_id`.
- Locate source audio files using:
  - `audio_file`, when present and usable;
  - otherwise `<input_dir>/<corpus_id>.wav`.
- Upload the audio to Gemini via the Files API, generate the content, and **strictly ensure** the file is deleted from Google's servers afterward using a `finally` block.
- Write plain-text descriptions as:

```plain text
<output_dir>/<corpus_id>.txt
```

- Write detailed JSON records as:

```plain text
<output_dir>/<corpus_id>.json
```

- Create the output directory if it does not already exist.
- Use `gemini-2.5-flash` by default, configurable via command-line argument.
- Use test mode by default, limiting processing to 1 eligible audio file initially.
- Skip already-described audio files by default, supporting safe re-runs.
- Allow reprocessing with an explicit command-line option.
- Support starting from a specific `corpus_id`.
- Implement a delay between requests to respect API rate limits.
- Continue processing remaining items if one API call fails.
- Record progress and errors in an append-only log file.
- Produce a JSON manifest with run-level metadata and item-level results.
- Write both:
  - a timestamped per-run manifest;
  - a latest manifest overwritten on each run.
- Write a curated description index (NDJSON) for downstream tasks.
- Exit with status code `0` only when all attempted calls succeed or are skipped, and there are no missing inputs or invalid eligible metadata rows.
- Exit with non-zero status code if one or more attempted calls fail, if source audio is missing, if eligible metadata is invalid, or if there is a configuration/validation error.

# 8. Core Processing Architecture

## 8.1 High-level flow

1. **Startup**: Parse args, resolve paths, load `.env`, setup logging, validate dependencies.
2. **Audio index loading**: Read index, select records where `download_status` is eligible.
3. **Planning**: Apply `--start-corpus-id`. Resolve audio paths. Check if `.txt` and `.json` already exist. Plan items or mark as `skipped_existing` / `missing_input`. Apply `--test-limit`.
4. **Client Initialization**: Instantiate `genai.Client()`. Read prompt file content into memory.
5. **Execution**:
   - For each planned item:
     - Upload file to Gemini (`client.files.upload`).
     - Generate content with the loaded prompt.
     - **Critically**: Delete file from Gemini (`client.files.delete` in `finally`).
     - Save `.txt` and `.json`.
     - Sleep for `--request-delay` seconds to respect rate limits.
     - Capture timing and errors, retry if necessary.
     - Mark item as `success` or `failed`.
6. **Description index generation**: Write NDJSON index mapping corpus IDs to their new description files.
7. **Manifest writing**: Save summary, latest manifest, and per-run manifest.
8. **Exit**: Return 0 for success, 1 for partial failures, 2 for config errors, 130 for interrupts.

# 9. API Call Behaviour

## 9.1 Upload and Cleanup

Uploading an audio file to Gemini takes up quota and storage. The script **must** use a `try...finally` block to ensure `client.files.delete(name=uploaded_file.name)` is called regardless of whether generation succeeds or fails.

## 9.2 Rate Limiting

The Gemini API enforces requests-per-minute (RPM) limits. A `--request-delay` parameter must be used to `time.sleep()` after each successful or failed attempt to prevent 429 Resource Exhausted errors.

## 9.3 Existing files

If both output files already exist and `--reprocess` is not enabled:
- do not call the API;
- mark the item as `skipped_existing`.

## 9.4 Missing source audio

If the expected source audio does not exist:
- do not call the API;
- mark the item as `missing_input`.

## 9.5 API failures

If generation raises an exception (e.g., `APIError`):
- capture the failure;
- retry up to `--max-retries` with a sleep of `--retry-delay`;
- if all retries fail, mark the debate as `failed`;
- continue with the next file;
- exit with code `1` after the run.
